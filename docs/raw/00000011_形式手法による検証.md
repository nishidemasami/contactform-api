# 00000011_形式手法による検証

本ドキュメントでは、`contactform-api` の `core/domain` クレートへの `#![no_std]` 導入および形式手法ツール（**Verus**・**Kani**）の適用を通じて得られた知見・ノウハウ、メリットとデメリット、理想と現実のトレードオフ、懸念事項、そして「なぜ `no_std` である必要があるのか」「なぜすべてのプログラムを形式手法で検証することができない／する必要がないのか」を網羅的にまとめる。

---

## 1. 形式手法（Formal Methods）の位置づけ

ソフトウェアの品質保証手法は、検証の深さとコストによって以下の階層に分かれる。

| 手法 | 代表ツール | 検証のアプローチ | 保証の範囲 | 得意な対象 |
|---|---|---|---|---|
| **型検査・静的解析** | `rustc`, `clippy` | 型システム・所有権・借用規則・lint | 型安全性、データ競合不在、一般的なアンチパターン | ワークスペース全体 |
| **単体・結合テスト** | `cargo test`, `pytest` | 開発者が選んだ具体的な入力例を実行 | 記述したテストケースのみ（点での確認） | 全レイヤー、外部連携（DB・HTTP） |
| **プロパティベーステスト** | `proptest` | ランダム生成した多数の入力で性質を検証 | 試行回数分（確率的確認、コーナーケースを取りこぼす可能性あり） | 入出力変換、シリアライザ、境界探索 |
| **有界モデル検査（BMC）** | **Kani**（CBMC） | ループ上限（境界）内の**全ビットパターン**を記号実行し SAT ソルバで網羅証明 | 境界内の**全入力（100%網羅）**・パニック不在・UB不在 | ビット演算、`core`/`alloc` を含む実コード、値オブジェクト・エンティティ |
| **演繹的検証（定理証明）** | **Verus**（Z3 / SMT） | 事前条件・事後条件・ループ不変条件を記述し SMT ソルバで数学的に帰納証明 | **任意長・非有界（無限の入力空間）**に対する完全な仕様充足・停止性 | 純粋アルゴリズム、データ構造不変条件、ドメイン核ルール |

単体テストが「いくつかの点を打ってバグがないか確かめる」のに対し、形式手法は**「仕様を満たさない反例が数学的に1つも存在しないことを証明する」**アプローチである。

## 2. 形式手法のメリットとデメリット

### 2.1. メリット

1. **コーナーケースの完全網羅（反例不在の数学的証明）**
   - 人間やランダムテストでは見落としやすい境界値（例：Unicode の多バイト境界、全角空白 `U+3000` や `U+202F`、整数オーバーフロー境界、`100` 文字ちょうどと `101` 文字の空白文字列など）を 1 つ残らず網羅できる。
2. **ランタイムパニック・未定義動作（UB）の根絶**
   - スライスの範囲外アクセス（`bytes[index]`）、算術オーバーフロー（`index + step`）、`unwrap()` 失敗などが絶対に起きないことをコンパイル・検証時に証明できる。
3. **暗黙の仕様・優先順位の明文化**
   - 形式仕様（`ensures`）を書く過程で、「101文字の空白のみの文字列が来たとき、`Empty` と `TooLong` のどちらを返すべきか？」といった曖昧な仕様の優先順位を厳密に定義せざるを得なくなり、設計品質そのものが向上する。
4. **AI駆動開発における最強のガードレール**
   - AIエージェントは一見もっともらしいコードや単体テストを通過するコードを書くのが得意である一方、微妙な境界バグやエッジケースの抜けを作り込むことがある。
   - Kani や Verus を CI に組み込むことで、AI が生成・変更したコードがドメイン不変条件を 1 ビットでも破れば機械的にリジェクトできる（数学的オラクルとして機能する）。

### 2.2. デメリット

1. **高い記述コストと専門知識の要求**
   - 演繹的検証（Verus）では、実装コードとは別に仕様関数（`spec fn`）、ループ不変条件（`invariant`）、停止性測度（`decreases`）、量化子のトリガー（`#[trigger]`）、補題（`proof fn`）を記述する必要がある。
   - 有界モデル検査（Kani）でも、ループ展開上限（`#[kani::unwind(N)]`）やシンボリック入力の構築方法を慎重に設計しないと検証が終わらない。
2. **状態爆発（State Explosion）と証明の脆さ（Proof Brittleness）**
   - わずかな実装変更（例：標準ライブラリのイテレータメソッドを1つ呼ぶ、`String::push` をループで呼ぶ）によって、CBMC の SAT 論理式が数百万節に膨張してタイムアウトしたり、Z3 がタイムアウト（rlimit 超過）したりすることがある。
3. **ツールチェーンへの強い依存（ロックイン）**
   - Verus は特定の Rust ツールチェーン（例：`1.100.0`）の内部コンパイラライブラリ（`librustc_driver`）にリンクして動作し、Kani も特定日付の Nightly コンパイラを内部で使用する。通常の Rust バージョンアップと足並みが揃わない場合がある。
4. **「仕様自体のバグ」は検出できない**
   - 形式手法が保証するのは「実装が形式仕様と一致していること」であり、形式仕様そのものがビジネス要件とズレている場合や、前提条件（`requires` / `kani::assume`）を絞りすぎて空疎な真（Vacuous Truth）になっている場合は防げない。

## 3. なぜ `no_std` である必要があるのか

`core/domain` を形式手法で検証するにあたり、まずクレートを `#![no_std]`（さらに検証コアである `validation.rs` は `alloc` も使わない純粋 `core` のみ）にしたのには、単なる組み込み対応ではなく**形式検証上の必然的な理由**がある。

### 3.1. OS・I/O・非決定的副作用のコンパイラレベルでの遮断

`std` にはファイルシステム、ネットワークソケット、システムクロック（`SystemTime::now`）、環境変数、スレッド、乱数、OS システムコール（`libc` / Linux syscall）が含まれる。
形式手法（SMT ソルバやモデルチェッカ）は、**「同じ入力に対して常に同じ出力を返す決定論的な数学関数（あるいは閉じた状態機械）」**を前提としている。OS カーネルや外部 I/O に到達するコードが含まれていると、以下の問題が起きる。

- **Kani**: 未対応の外部 C 関数（foreign function）やシステムコール、インラインアセンブリに到達した時点で検証失敗となる。
- **Verus**: 外部副作用を持つ関数には原理的に純粋な仕様を与えられず、`external_body` として検証対象外に逃がすしかなくなる。

`#![no_std]` を指定し、`Cargo.toml` で依存クレートの `std` フィーチャ（`chrono` の `clock` 等）を無効化することで、**ドメイン層に非決定的な I/O やシステム時刻取得が紛れ込むことをコンパイラが物理的に禁止**してくれる。

### 3.2. 検証状態空間（State Space）の極小化

`std` が有効な環境では、一見単純な処理の裏側でパニックハンドラ、バックトレース収集、スレッドローカル変数、フォーマット処理、OS アロケータ連携などの膨大なコードがリンクされる。
CBMC（Kani）は到達可能なすべての制御フローとメモリ操作を論理式（SSA 形式）に変換するため、`std` 依存を引きずると生成される論理式が巨大化し、検証時間が桁違いに悪化する。

さらに、`core/domain` 内でも：
- 外側の値オブジェクト（`value_object.rs`）は `#![no_std]` + `alloc`（`String` 保有）
- 内側の検証コア（`validation.rs`）は **`#![no_std]` かつ `alloc` 非依存（`core` のみ）**

という二段構成を採ることで、ヒープメモリ確保（`malloc` / `realloc` / 容量計算オーバーフロー分岐）に伴う状態爆発すら完全に排除し、ミリ秒〜数秒単位での高速な形式検証を実現している。

### 3.3. クリーンアーキテクチャの徹底と将来のポータビリティ

DDD・クリーンアーキテクチャにおいて「`domain` は他のいかなるレイヤーやインフラにも依存しない」という原則があるが、`#![no_std]` はこれを最も厳格に強制する仕組みでもある。副次的メリットとして、将来的にこの `domain` クレートを WebAssembly（`wasm32-unknown-unknown`）にコンパイルし、フロントエンド（Next.js）とバックエンド（Lambda）で**形式検証済みの同一バリデーションロジックを共有**することも容易になる。

## 4. なぜすべてのプログラムを形式手法で検証することができない／する必要がないのか

「形式手法がそれほど強力なら、API 全体（`application`, `infrastructure`, `presentation`, `lambda`）もすべて Kani や Verus で証明すべきではないか？」という疑問が自然に生じる。しかし、それは**技術的に不可能（または非現実的）**であり、同時に**工学的にも行うべきではない**。

### 4.1. 技術的に「検証できない」理由

1. **外部世界には形式モデルが存在しない（モデリングの限界）**
   - AWS Lambda ランタイム、API Gateway、TLS 通信、Amazon Aurora DSQL / PostgreSQL サーバー、Linux カーネルの実際の振る舞いは、Rust コードの外側にある物理・分散システムである。
   - 形式検証で DB アクセスを扱おうとしても、「DB はこのように動くはずだ」というモック（仮定）に対して証明することしかできず、**実際の SQL 構文エラーや IAM 権限不足（例：Aurora DSQL の INSERT 専用ロールで `RETURNING` 句が拒否される問題）は一切検出できない**。
2. **巨大エコシステム・非同期ランタイムの壁**
   - `tokio`（マルチスレッド／非同期スケジューラ、epoll、`unsafe` ポインタ操作）、`sea-orm` / `sqlx`、`hyper`、`rustls`、AWS SDK などの外部クレートは数十万行規模のコードと複雑なマクロ・動的ディスパッチ・FFI を持つ。
   - Verus はこれら未検証クレートをそのまま解釈できず、Kani でも非同期ランタイムや暗号・通信スタックを通すと即座に状態爆発または未サポート構文エラーに突き当たる。
3. **計算量理論上の限界（決定不能性とソルバの限界）**
   - 一般のプログラムの性質検証は計算理論上決定不能（停止性問題）であり、SMT/SAT ソルバも万能ではない。特に非線形算術（64ビット整数の除算・剰余の連鎖）、複雑なビット並列最適化（標準ライブラリの SWAR / SIMD 文字列処理）、深いヒープ構造の比較などはソルバの探索空間を指数関数的に爆発させる。

### 4.2. 工学的に「検証する必要がない（すべきではない）」理由

1. **費用対効果（ROI）と変更容易性のトレードオフ**
   - 100 行のコードに完全な形式証明を付与するには、しばしば数百行の仕様・不変条件・補題・ハーネス設計が必要になる。
   - リクエスト JSON から DTO への詰め替えや HTTP ステータスコード変換のような「一目で分かる単純な配線コード」や「仕様変更が頻繁に入る外周レイヤー」に形式証明を課すと、保守コストばかりが膨れ上がりアジリティを失う。
2. **レイヤーごとに「発見したいバグの種類」が異なる（適材適所の検証戦略）**

| レイヤー | 主な責務 | 発生しやすいバグ | 最適な検証手法（本プロジェクトの方針） |
|---|---|---|---|
| **`domain`（核）** | ドメインモデル・不変条件・バリデーション | 境界値ミス、文字コード／空白判定漏れ、条件優先順位ミス、パニック | **形式手法（Verus + Kani）** ＋ 単体テスト |
| **`application`** | ユースケース制御・リポジトリ呼び出し | 呼び出し順序ミス、エラー変換漏れ | モックを用いた **単体テスト（`cargo test`）** |
| **`infrastructure`** | SeaORM による SQL 発行、DSQL 接続 | SQL 構文ミス、プレースホルダー不整合、`RETURNING` 句等の DB ロール権限違反 | 実 PostgreSQL + Liquibase を用いた **DB 結合テスト** |
| **`presentation` / `lambda`** | HTTP ルーティング、JSON 入出力、OpenAPI | パス／メソッド分岐ミス、シリアライズ不整合、Lambda イベント連携ミス | 単体テスト ＋ **`sam local start-api` & `pytest` 結合テスト** ＋ OpenAPI 自動生成 |

このように、**「外部との接合部は実環境に近い結合テストで叩き、純粋なビジネスルールの核（Core）は `no_std` に隔離して形式手法で数学的に固める」**という組み合わせこそが、コストと信頼性を最大化するソフトウェア工学上の最適解である。

## 5. 理想と現実：設計パターンの比較と採用したベストプラクティス

`core/domain` に Verus を適用する際、アーキテクチャ上は以下の 2 つの設計パターンが存在する。

### 5.1. パターン比較：クレート統合インライン方式 vs Verified Core 分離方式

| 比較軸 | 【理想】クレート統合・インライン方式（Verus-First） | 【現実解・採用】Verified Core 分離方式（Functional Core, Imperative Shell） |
|---|---|---|
| **構造** | `domain/Cargo.toml` に `vstd` と `[package.metadata.verus]` を追加し、`value_object.rs` の `InquiryName` 等に直接 `verus!` / `#[verifier::type_invariant]` を記述する | 純粋検証ロジックを外部依存ゼロの `validation.rs` に切り出して Verus で検証し、`value_object.rs` はそれを呼ぶ薄いラッパーにして Kani で検証する |
| **仕様の局所性** | 高い（値オブジェクト構造体と形式仕様が同一ファイルに並ぶ） | 中程度（型定義は `value_object.rs`、形式仕様は `validation.rs` に分かれる） |
| **型不変条件の保証** | `InquiryName` 型自体の不変条件（`wf`）まで Verus 単体で完結する | `validate_field_utf8` までを Verus が証明し、ラッパーの数行の `match` と値保持は Kani が証明する |
| **本番 `Cargo.toml` への影響** | `vstd = "=0.0.0-..."` のピン留めが必要になり、本番ビルドの依存グラフに混入する | **`Cargo.toml` / `Cargo.lock` への追加依存ゼロ** |
| **Rust バージョン制約** | クレート全体のビルドが Verus 指定の Rust バージョン（例：`1.100.0`）に縛られ、既存 CI（`1.97.1`）と衝突しやすい | 通常ビルド（`1.97.1`）と Verus 実行環境（`1.100.0`）を疎結合に保てる |
| **`no_std` / `--all-features` 整合** | `vstd` はデフォルトで `std` を要求するため、`x86_64-unknown-none` や `--all-features` ビルドで壊れやすい | 問題なく両立する |
| **`--no-cheating` の可否** | `Uuid` / `DateTime` / `Into<String>` 境界に `external_body` や `assume_specification` が必要になり、`--no-cheating` が使えない | **公理・仮定ゼロの `--no-cheating` で完全検証可能** |

### 5.2. 本プロジェクトで採用したハイブリッド構成

既存の AWS Lambda / SeaORM ワークスペースとの整合性、本番依存のクリーンさ、および `--no-cheating` による厳格な証明を重視し、本プロジェクトでは **Verified Core 分離方式 ＋ Verus / Kani ハイブリッド検証** を採用した。

```text
[value_object.rs / entity.rs]  (#![no_std] + alloc + uuid + chrono)
  │  └─ Kani が検証：
  │       ・InquiryName / InquiryEmail / InquiryMessage の生成・エラー変換・値保持
  │       ・InquiryId (UUID) / Inquiry エンティティ全フィールド保持
  ▼
[validation.rs]  (純粋 #![no_std] / alloc なし / 外部クレートなし / unsafe なし)
  ├─ Verus が検証（--no-cheating / 任意長入力）：
  │    ・UTF-8 単一パス走査の安全性・停止性・オーバーフロー不在
  │    ・空判定優先順位（空白101文字 → Empty）・上限境界厳密性（100 / 256 / 5000）
  └─ Kani が橋渡し検証（全 1,112,064 通りの Unicode char 網羅）：
       ・is_unicode_whitespace(ch) == core::char::is_whitespace(ch) の完全一致
       ・decode_utf8_codepoint_at が char::encode_utf8 の完全な逆写像であること
```

注目すべき点は、**「Verus で検証するために自前で書いた UTF-8 デコーダや Unicode 空白判定関数自体にバグや標準ライブラリとのズレがないか？」という問題を、Kani による全 `char`（1,112,064 通り）の網羅証明で完全に塞いでいる**ことである。これが Verus（非有界の帰納証明）と Kani（標準ライブラリ実装とのビット精密な同値証明）を組み合わせる最大の強みである。

## 6. 実装から得られた実践ノウハウ・知見

### 6.1. Verus のノウハウ

1. **`#[cfg_attr(verus_keep_ghost, ...)]` による通常 Rust との共存**
   - ファイル全体を `verus! { ... }` マクロで囲むと、`rustfmt` が効かなくなったり通常の `rustc` / `clippy` と相性問題が出たりしやすい。
   - 実行関数（exec 関数）は通常の Rust 構文で書き、`#[cfg_attr(verus_keep_ghost, verus_builtin_macros::verus_spec(...))]` とループ内の `#[cfg(verus_keep_ghost)] verus_builtin_macros::verus_proof_expr!({ ... })` を使うことで、**通常ビルド時は完全にマクロが消去されてゼロオーバーヘッドの標準 Rust コードになり、`rustfmt` や `clippy` もそのまま通る**。
2. **定数・列挙型の仕様公開**
   - `verus!` ブロック外の `pub const` はそのままでは Verus から参照できないため、`#[cfg_attr(verus_keep_ghost, verus_builtin_macros::verus_spec)]` を付与する。
   - 外部定義の単純な `enum` は `#[verifier::external_type_specification]` でラッパー構造体を宣言することで、`verus_spec` 内でもパターンマッチや等値比較が可能になる。
3. **量化子（`forall` / `exists`）のトリガー明示**
   - `exists|i: int| 0 <= i < chars.len() && ...` のような量化子を使う際、`#[trigger]` を明示しないと Verus が低信頼度トリガー警告を出すほか、SMT ソルバのインスタンス化が不安定になる。必ず適切な部分式に `#[trigger]` を付ける。
4. **`--no-cheating` の徹底**
   - AI に証明を書かせると、証明に詰まった際に `assume(false)` や `admit()`、`#[verifier::external_body]` を使って「証明したふり」をしてしまうリスクがある。CI では必ず `--no-cheating` を付けて実行し、抜け道を機械的に禁止する。

### 6.2. Kani のノウハウ（CBMC 状態爆発の回避パターン）

Kani（CBMC）では、「人間にとって短い標準ライブラリ呼び出し」が裏側で巨大なビット演算や双方向ループに展開され、SAT ソルバが数分以上ハングする現象が頻発する。今回の実装で実際に遭遇し解決したパターンを記録する。

| 詰まりやすいコード（アンチパターン） | 遅くなる原因（CBMC 内部の挙動） | 高速・確実に通す解決パターン |
|---|---|---|
| 任意バイト列 `[u8; N]` に `core::str::from_utf8` を通す | 標準ライブラリの `run_utf8_validation` がチャンク単位の最適化ループを持ち、ネストしたループ展開で論理式が爆発する | `let ch: char = kani::any();` を使い（Kani は有効な Unicode スカラー値のみを自動制約生成する）、`ch.encode_utf8(&mut buf)` で妥当な UTF-8 スライスを作る |
| シンボリック文字列に対して `str::trim()` を呼ぶ | `DoubleEndedSearcher` により前方・後方からの複雑な UTF-8 デコード状態機械が生成され SAT ソルバがハングする | `is_unicode_whitespace(ch) == ch.is_whitespace()` を全 `char` で証明したうえで、文字列側は `chars` 配列に対する `iter().all(char::is_whitespace)` と比較する |
| シンボリック文字列に対して `str::chars().count()` を呼ぶ | 標準ライブラリの `count` は 1 文字ずつ数えず、SWAR（ワード単位のビット並列トリック）最適化コードを通るため SAT ソルバ負荷が高い | 短い固定長スライスでは `Chars::next()` を明示的に呼ぶか、エンコード元の `char` 配列長 `len` を使う |
| `chrono::Utc.timestamp_opt(secs, nsecs)` にシンボリック `i64` を渡す | 経過秒数から閏年・月日を算出する 64 ビット整数の除算・剰余（`from_num_days_from_ce_opt`）が SAT ソルバにとって極めて重い | 日付計算自体の検証が目的でなければ、固定 `NaiveDate` ＋ 除算なしの `NaiveTime::from_num_seconds_from_midnight_opt(secs, nsecs)` ＋ シンボリック `FixedOffset` で構築する |
| `Uuid` 同士をそのまま `assert_eq!(a, b)` で比較する | `[u8; 16]` の `memcmp` ループ（16回反復）が生成され、小さい `#[kani::unwind(4)]` 指定に引っかかって unwinding failure になる | `assert_eq!(a.as_u128(), b.as_u128())` として単一の 128 ビット整数比較に落とす |
| ループ内で `String::push` を繰り返して入力を作る | `Vec` の容量チェック・再アロケーション・レイアウト計算パスが毎回分岐生成される | スタック上の固定長配列（`[u8; 8]` 等）に `encode_utf8` で書き込んで `&str` スライスを作る |

## 7. 懸念事項・リスクと運用上の注意点

1. **CI 実行時間への影響**
   - 現在、`validate-ci.yaml` および `api-cicd.yaml` で毎回 `kani-verifier` の `cargo install`・バンドル取得および Verus のダウンロード・ツールチェーン取得を行っているため、CI 時間が数分増加する懸念がある。
2. **ツールバージョンと Rust 本体の非同期な進化**
   - Rust の新エディションや新構文を `domain` で使った際、Kani（内部 Nightly）や Verus（特定 Stable）が未対応で CI が落ちる可能性がある。バージョンアップ時は必ず固定バージョン（現在 Verus `0.2026.11.22.1ce6a59`、Kani `0.68.0`）の動作確認を行う。
3. **前提条件（`kani::assume` / `requires`）の誤用による「空疎な証明」リスク**
   - 例：矛盾する `kani::assume` を書くと、以降の `assert!` が何であっても常に検証成功してしまう。新しいハーネスを追加する際は、意図的にアサーションを反転させて一度 FAIL することを確認するか、通常の単体テスト（具体値テスト）を必ず併設する。
4. **証明済み範囲と未証明範囲の境界認識**
   - 現在の `InquiryEmail` のドメインルールは「空でないこと」「256文字以内であること」であり、その範囲は 100% 形式証明されているが、RFC 5322 準拠のメールアドレス構文（`@` の有無など）はそもそも現在のドメイン仕様に含まれていない。「形式検証済み ＝ あらゆるビジネス上の妥当性が保証済み」と過信せず、何が仕様として定義されているかを常に意識する必要がある。

## 8. 今後のより良い改善案

1. **【短期】CI における Verus / Kani ツールキャッシュの導入**
   - GitHub Actions の `actions/cache` を利用して `~/.kani`、`~/.local/verus`、および `cargo-kani` バイナリをキャッシュし、`cargo install kani-verifier` の毎回ビルドを省略して CI 実行時間を短縮する。
2. **【中期】ドメイン仕様の拡充に合わせた Verified Core の拡張**
   - メールアドレスの形式チェック、制御文字（ヌル文字等）の混入禁止ルール、将来的な問い合わせステータス遷移（未対応 → 対応中 → 完了などの状態機械）が追加された際、`validation.rs` と同様に純粋 `no_std` モジュールとして実装し Verus・Kani で不変条件を証明する。
3. **【長期】`cargo verus` インライン型不変条件（パターンB）への統合検討と Wasm 共有**
   - 将来的にワークスペース全体の Rust ツールチェーン統一や `vstd` の `no_std` 対応が成熟した段階で、`#[verifier::type_invariant]` を用いて `value_object.rs` の構造体自身に不変条件を持たせるインライン方式への移行を再評価する。
   - また、`#![no_std]` 化した `domain` クレートを WebAssembly としてビルドし、フロントエンド（`frontend/`）のフォームバリデーションと単一の検証済み実装を共有するアーキテクチャも有力な発展方向である。
