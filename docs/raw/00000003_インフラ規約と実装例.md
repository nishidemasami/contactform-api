# 00000003_インフラ規約と実装例 (AWS SAM & サーバレスアーキテクチャ設計)

本ドキュメントは、本システムにおけるAWS SAMを用いたインフラ構築、AWS上のサーバレスアーキテクチャ設計、およびIaCやCI/CDのベストプラクティスを定めた規約である。本システムに関わるすべての開発者（人間およびAIエージェント）は、本規約を遵守して設計・実装およびデプロイ手順の構築を行わなければならない。

---

## 1. AWS SAMによるインフラ構築のベストプラクティス

本プロジェクトでは、保守性、拡張性、およびデプロイ時の安全性を最大化するために、IaCツールとしてAWS SAMを使用し、以下の設計ベストプラクティスを採用する。

- 原則として、Lambda FunctionName、S3 BucketName、IAM RoleName などの物理名は明示指定せず、CloudFormation/SAMによる自動命名を利用する。
  - これにより、リソース置換時の名前衝突を避け、スタック更新時の失敗リスクを低減する。
  - ただし、自動命名は `ROLLBACK_COMPLETE` や `UPDATE_ROLLBACK_FAILED` の発生そのものを防ぐものではない。
- スタックが `ROLLBACK_COMPLETE` や `UPDATE_ROLLBACK_FAILED` などのステータスになった場合でもスタックの削除を局所的に実施できるように、スタックは `AWS::Serverless::Application` で親子関係にせず、スタック間の値の受け渡しは`AWS::SSM::Parameter`を経由する

### 1.1. スタックの疎結合化とパラメータ連携（SSM Parameter Storeの活用）
AWS CloudFormationの `Outputs` による `Export` と `Fn::ImportValue` を用いた連携は、スタック間に強固な依存関係（密結合）を生み出し、スタックの更新や削除を困難にする（スタックのロック状態の発生）。そのためスタック間連携では、原則として `Fn::ImportValue` によるクロススタック参照を避け、SSM Parameter Storeを介して値を受け渡す。

ただし、SSM Parameter Store経由の値は、参照側スタックの作成または更新時に解決されるため、参照元パラメータの変更が参照側リソースへ自動反映はされない。パラメータ変更後は、参照側スタックの再デプロイを行うが、強いライフサイクル依存を意図的に持たせたい基盤リソースでは、例外的にExport/ImportValueを許可する。

- **ルール**: 他のスタックで定義されたリソースを参照する場合、ImportValueを使用せず、SSM Parameter Storeから値を動的に参照する。
- **メリット**: スタック同士のライフサイクルが分離され、個別のデプロイや一時的な削除、リプレイスが安全に行える。

### 1.2. SSMパラメータ命名規則
設定値の混同やバッティングを防ぐため、パラメータ名は以下の階層構造で厳格に定義する。

`/{環境名}/{サービス名}/{サブシステム名}/{パラメータ名}`

- **環境名（Stage）**: `develop`（開発/テスト環境）または `release`（本番環境）
- **サービス名**: `example-service` ※サービス名はCloudFormationのStack名にも使われるため記号はハイフンのみ。
- **サブシステム名**: `api`, `auth`, `db`, `frontend`, `review`, `retained`
- **パラメータ名**: キャメルケースで記述（例: `ApiGatewayDomain`, `DSQLEndpoint`）

以上のうち、「環境名」「サービス名」はCI/CDの`info`ステップの`outputs`で出力する。

| 概要 | 項目名 |
|---|---|
| **環境名（Stage）** | `stage` |
| **サービス名** | `service_name` |

#### 定義パラメータ一覧
本システムで管理・連携するパラメータは以下の通り。

| 概要 | サブシステム名 | パラメータ名 | 登録される値（Value） |
|---|---|---|---|
| API GatewayのエンドポイントURL | `api` | `ApiGatewayDomain` | `!Select [2, !Split ["/", !GetAtt <HttpApiリソース>.ApiEndpoint]]` |
| Aurora DSQLのエンドポイント | `db` | `DSQLEndpoint` | `!GetAtt <AWS::DSQL::Clusterリソース>.Endpoint` |
| DB（DSQL）アクセス用Lambda実行ロールのARN | `db` | `DbConnectLambdaRole` | `!GetAtt <AWS::IAM::Roleリソース>.Arn` |
| フロントエンド公開用CloudFrontドメイン名 | `frontend` | `DomainName` | `!GetAtt <CloudFrontリソース>.DomainName` |
| フロントエンド公開用CloudFrontディストリビューションID | `frontend` | `DistributionID` | `!Ref <CloudFrontリソース>` |
| フロントエンドSPA格納S3バケット名 | `retained` | `FrontendBucketName` | `!Ref <フロントエンドSPA格納S3リソース>` |
| フロントエンドSPA格納S3のWebsiteURL | `retained` | `FrontendWebsiteURL` | `!GetAtt <フロントエンドSPA格納S3リソース>.WebsiteURL` |
| レビュー資料格納S3バケット名 | `retained` | `ReviewBucketName` | `!Ref <レビュー資料格納S3>` |
| レビュー資料格納S3のWebsiteURL | `retained` | `ReviewWebsiteURL` | `!GetAtt <レビュー資料格納S3>.WebsiteURL` |

### 1.3. マルチスタック（ディレクトリ）構成
本プロジェクトはモノレポ構成を採用しており、インフラ定義ファイル（`template.yaml`）は役割ごとに以下のサブシステム配下に分割して管理する。これにより、変更影響を局所化し、デプロイ時間を短縮する。

```text
├── api/
│   └── template.yaml     # API基盤（AWS::Serverless::Function, AWS::Serverless::HttpApiなど）
├── auth/
│   └── ~~template.yaml~~     # 認証基盤（AWS::Cognito::UserPool, AWS::Cognito::UserPoolClientなど）（今回は無いため省略）
├── db/
│   └── template.yaml     # DB基盤（AWS::DSQL::Cluster, AWS::IAM::Roleなど）
├── frontend/
│   └── template.yaml     # フロントエンド基盤（CloudFront Distributionなど）
├── retained/
│   └── template.yaml     # 認証やS3、DynamoDBなどの決して削除されるべきではない永続的なインフラ（DSQLは別途管理）
└── review/
    └── ~~template.yaml~~     # レビュー資料管理用基盤（今回はS3をretainedに定義しており、ここにはなにも無いため省略）
```

### 1.4. 全 `template.yaml` 共通仕様
すべての `template.yaml` で環境の切り替えとサブシステムの識別を行えるよう、共通の `Parameters` と `Conditions` を定義する。

```yaml
Parameters:
  ServiceName:
    Type: String
    Default: example-service
    AllowedValues:
      - example-service
    Description: "The name of the Service"
  Stage:
    Type: String
    Default: develop
    AllowedValues:
      - develop
      - release
    Description: "Target deployment environment stage (develop or release)"
  SubSystem:
    Type: String
    AllowedValues:
      - api
      - db
      - frontend
      - review
    Description: "The name of the subsystem being deployed"
    
Conditions:
  IsRelease: !Equals [!Ref Stage, release]
```

## 2. AWSにおけるサーバレスアーキテクチャのベストプラクティス

本システムは、高いスケーラビリティの確保、運用負荷の最小化、および長期間の保守容易性を満たすため、AWSのリージョナルなサーバレスサービス（Amazon API Gateway, AWS Lambda, Amazon Aurora DSQL, Amazon S3, Amazon CloudFrontなど）のみを組み合わせて構築する。

### 2.1. インフラ選択基準
- **採用サービス**: EC2、RDS、Lightsail、ECS、EKSなどの「OSやパッチ管理や運用保守を必要とするコンテナ・VMサービス」は**一切使用しない**。
- **背景**: サーバレスサービスのみで構成することで、ゼロスケールによりコストを最小化し、インフラ保守管理コストを最小化する。

### 2.2. API実装について
本システムは、APIの実行性能とコストパフォーマンスの最適化を目的として、AWS Lambdaは**Rust (provided.al2023) × ARM64 アーキテクチャ**、Amazon API Gatewayはv2(HTTP API)を採用する。

#### ① Lambdaメモリ設定とCPU性能の最適化

AWS Lambdaでは、関数に割り当てたメモリ量に比例してCPU性能も割り当てられる。1769MBで1vCPU相当となり、128MBではAWSの現環境では約0.08コア（1/12コア）相当となっている。
128MBは最小構成であり、IOバウンド処理やネットワークバウンド処理などの軽量なAPIには有効だが、CPUバウンド、初期化処理が重い関数では、メモリを増加するによりレイテンシとコスト効率が改善する可能性がある。

本プロジェクトでは、初期値として128MBを採用するが、以下のメトリクスをもとに継続的にチューニングする。

- p50 / p95 / p99 レイテンシ
- Cold Start時間
- Billed Duration
- Max Memory Used
- エラー率
- コスト

必要に応じて、256MB、512MB、1024MB、1769MBなど複数設定でベンチマークし、最適値を決定する。

#### ② CPUブースト機能（INITフェーズ）の有効活用
- **原理**: AWS Lambdaではメモリ量に比例してCPU性能が割り当てられる。128MBは最小構成であるため、初期化処理や暗号化、DB接続確立、JSON処理が重い場合はレイテンシが悪化することがある。初期方針としてはINITフェーズへ重い処理を寄せるが、CPUブーストの有無や効果を前提にしすぎず、実測で判断する。
- **設計指針**:
  - DB接続の初期化、環境変数のパース、AWS SDK設定のロード、ロガーの起動などの「オーバーヘッドが大きく重い処理」は、すべて `main` 関数内の初期化処理（INITフェーズ）に詰め込んで完了させる。
  - INITフェーズが10秒を超えてしまうと初期化失敗とみなされ、CPUブースト枠が失われた状態でリトライされてしまうため、**1/12コアでも10秒以内で初期化が完結するように実装する**。

#### ③ 低メモリ構成でのINVOKEフェーズのシングルスレッド最適化
- **原理**: 低メモリ構成では、初期化完了後の `INVOKE`（リクエスト処理）フェーズに入ると、CPUは制限される。マルチスレッドのコンテキストスイッチやスレッド間排他制御のオーバーヘッドが処理遅延（レイテンシ悪化）の原因となるため、初期方針としてシングルスレッドでの実装とする。ただいｓ、CPUバウンド処理などはメモリを増やした上で `multi_thread` の採用を検討する。
- **設計指針**:
  - 非同期ランタイム `tokio` のマクロ設定で、明示的にシングルスレッド（`current_thread`）を指定する。
  ```rust
  #[tokio::main(flavor = "current_thread")]
  async fn main() {
      // エントリポイント
  }
  ```
  - 低メモリ構成では以上のように実装し応答性能を最適化する。

```yaml
  ServiceName:

    Default: example-service
    AllowedValues:

  # --parameter-overrides Stage="${{ steps.info.outputs.stage }}"

    Type: String
    Default: develop
    AllowedValues:
      - develop
      - release
    Description: "Target deployment environment stage (develop or release)"
  # --parameter-overrides SubSystem="api"

    Type: String
    AllowedValues:

      - retained

    Type: AWS::SSM::Parameter::Value<String>
  # --parameter-overrides DSQLEndpoint="/${{ steps.info.outputs.stage }}/${{ steps.info.outputs.service_name }}/db/DSQLEndpoint"
  DSQLEndpoint:
    Type: AWS::SSM::Parameter::Value<String>

    Type: String

  ApiFunction:
    Type: AWS::Serverless::Function
    Properties:
      CodeUri: ./lambda
      Handler: bootstrap # `Cargo.toml`の`[[bin]]`で指定する`name`を設定
      Runtime: provided.al2023
      Architectures:
        - arm64
      Timeout: 10
      MemorySize: 128
      Environment:
        Variables:
          DSQL_ENDPOINT: !Ref DSQLEndpoint
      Role: !Ref DbConnectLambdaRole
      # # 例：Lambda関数URLで公開する場合
      # FunctionUrlConfig:
      #   AuthType: NONE # パブリックに公開する
      #   InvokeMode: BUFFERED # 通常のレスポンス（ストリーミングを使わない）
      # 例：API Gatewayで公開する場合
      Events:
        ApiEvent:
          Type: HttpApi
          Properties:
            ApiId: !Ref HttpApiGateway
            Path: /{proxy+}
            Method: ANY
    Metadata:
      BuildMethod: rust-cargolambda
      # 複数の[[bin]]があるので、BuildProperties.Binaryの値を指定しなければ対象のバイナリをSAMが判断できません。
      BuildProperties:
        Binary: bootstrap # `Cargo.toml`の`[[bin]]`で指定する`name`を設定
  HttpApiGateway:
    Type: AWS::Serverless::HttpApi
    Properties:

      # 実際の値は、API Gatewayの許容RPS、Lambda同時実行数、DB接続プールサイズ、Aurora DSQL側の接続・書き込み制限を合わせて設計する。
      DefaultRouteSettings:
        ThrottlingRateLimit: 1   # 1秒あたりの平均リクエスト数 (RPS)
        ThrottlingBurstLimit: 100  # 同時に処理できる最大バースト数（DSQLの最大接続レート制限（ハード上限）の秒間 100 コネクションに設定）
      # CORS 設定。
      # ブラウザから別オリジンで API を叩く場合に必要です。
      CorsConfiguration:
        AllowOrigins:
          - !Ref CORSOrigin
        # 許可する HTTP メソッド。
        # プリフライト(OPTIONS)も含めています。
        AllowMethods:
          - GET
          - POST
          - PUT
          - DELETE
          - OPTIONS
        # ブラウザから送信を許可するリクエストヘッダ。
        AllowHeaders:
          - Content-Type
        # 認証情報（Cookieや認可ヘッダー）を含めない
        AllowCredentials: false 
  # SSMに値を出力
  ApiGatewayDomainParameter:
    Type: AWS::SSM::Parameter
    Properties:
      Name: !Sub "/${Stage}/${ServiceName}/${SubSystem}/ApiGatewayDomain"
      Type: String
      Value: !Select [2, !Split ["/", !GetAtt HttpApiGateway.ApiEndpoint]]
      Description: "API Gateway Endpoint URL"
  # # 例：Lambda関数URLで公開する場合
  # FunctionUrlParameter:
  #   Type: AWS::SSM::Parameter
  #   Properties:

  #     Type: String
  #     Value: !Select [2, !Split ["/", !GetAtt ApiFunction.FunctionUrl]]
  #     Description: "API Lambda Function URL"
```

### 2.3. CDNについて
最小特権原則（Least Privilege）と、インターネット公開時の境界防御設計を徹底する。

#### ① IAM最小特権の徹底（DBアクセス制御）
- **設計**: DB（Amazon Aurora DSQL）に対するLambdaのアクセス権限は、インサイトデータの保全性を守るため、必要最小限の権限のみを付与する。
- **具体例**: 問い合わせ投稿を行うLambdaの実行ロールには、`inquiries` テーブルに対する **`INSERT` 権限のみ**を付与し、`SELECT`（データ読み取り）や `UPDATE` / `DELETE` 権限は与えない。
- **Rust実装との整合**: `SELECT` 権限がないため、ORM（SeaORM）の `ActiveModel::insert` 内部で自動実行される `RETURNING`（自動インクリメントIDや生成値の暗黙的SELECT）が権限エラーとなる。そのため **SQLステートメント（`execute_raw`）やRETURNINGを伴わないINSERT(`exec_without_returning`)を用いたINSERT処理を行う**。（詳細は『[00000006_DB規約と実装例](./00000006_DB規約と実装例.md)』を参照のこと）。また、SQLステートメントを用いる場合にはSQLインジェクションを考慮しプレースホルダー付きSQLステートメントを使用する。

#### ② CloudFrontとS3によるセキュアな静的サイト配信

- **推奨構成**: 静的SPAおよびレビュー資料の配信は、原則として **CloudFront + S3 REST API origin + Origin Access Control (OAC)** を採用する。S3 Bucket は Public Access Block を有効にし、インターネットから直接 `s3:GetObject` できない状態を標準とする。
- **SPAルーティング対応**: S3 Website Hosting を使わずにSPAのクライアントサイドルーティングを実現する場合は、CloudFrontのCustom Error Responseで 403/404 を `/index.html` にフォールバックするか、CloudFront Functionで拡張子のないURIを `/index.html` にrewriteする。
- **例外構成**: S3 Website EndpointをCloudFrontのCustom Originとして使用する構成は、OAC/OAIを利用できないため、原則として推奨しない。やむを得ず採用する場合は、`aws:Referer` による制御は偽装可能な簡易防御であり、秘匿性や厳密な直接アクセス防止を保証しないことを明記する。
- **設計判断**: セキュリティを優先する本番環境ではOAC方式を標準とする。開発・検証用途でWebsite Endpoint方式を使う場合も、機密情報や非公開資料は配置しない。

#### ※補足：CloudFrontとS3による非セキュアな静的サイト配信
- 非セキュアな静的サイト配信が許容される場合、S3バケットはS3ウェブサイトホスティング機能によりインターネットに直接公開（Public Access）し**Amazon CloudFrontを経由することによりパフォーマンスの向上を図る**実装を許容する。
- S3ウェブサイトホスティングを利用してSPAを動作させる際には、簡易的に直接アクセスを防ぐことを目的として、CloudFrontからS3へのリクエストに**カスタムヘッダー（`aws:Referer` に、RFC 7230に準拠した文字列を設定）を付与**し、S3側で「この特定Refererを持つリクエストのみ許可する」ポリシーを定義する。※`aws:Referer`は偽装可能なため、直接アクセスを必ず防げるものではない。あくまでもパフォーマンスの向上施策として使用し、厳密なアクセス制限が必要な場合にはOAC方式を採用すること。

#### ③ CloudFrontのキャッシュ・配信設計
- **プロトコルセキュリティ**: HTTPアクセスはすべて自動的にHTTPSにリダイレクト（`ViewerProtocolPolicy: redirect-to-https`）する。
- **HTTPバージョン**: ネットワーク効率最大化のため、HTTP/2およびHTTP/3を有効化（`HttpVersion: http2and3`）する。
- **キャッシュポリシーの最適化**:
  - 静的コンテンツ（SPA / レビュー用資料）: `658327ea-f89d-4fab-a63d-7e88639e58f6` (CachingOptimized) を使用し、高いキャッシュヒット率とエッジ側でのgzip/brotli圧縮（`Compress: true`）を有効にする。
  - APIエンドポイント（`/api/*`）: `4135ea2d-6df8-44a3-9df3-4b5a84be39ad` (CachingDisabled) を設定し、バックエンドAPIに対するリアルタイムな疎通を保証する。また、ブラウザのホスト情報をバックエンドで正確に判定できるよう、オリジンリクエストポリシーに `b689b0a8-53d0-40ab-baf2-68738e2966ac` (AllViewerExceptHostHeader) を設定する。
- **価格クラス**: エッジロケーションに日本が含まれている「価格クラス200（`PriceClass_200`）」を採用する。

#### ④ 実装例

```yaml
Parameters:
  # --parameter-overrides ApiGatewayDomain="/${{ steps.info.outputs.stage }}/${{ steps.info.outputs.service_name }}/api/ApiGatewayDomain"
  ApiGatewayDomain:
    Type: AWS::SSM::Parameter::Value<String>

Resources:
  # 静的ファイル格納用S3バケット例
  StaticWebsiteBucket:
    Type: AWS::S3::Bucket
    # releaseステージはデータ保護のため削除を禁止し、developステージは環境の再作成を容易にするため削除を許可する
    DeletionPolicy: !If [IsRelease, Retain, Delete]
    UpdateReplacePolicy: !If [IsRelease, Retain, Delete]
    Properties:
      # パブリックアクセスブロックを部分的に解除（バケットポリシーで公開するため）
      PublicAccessBlockConfiguration:
        BlockPublicPolicy: false
        RestrictPublicBuckets: false
        BlockPublicAcls: true
        IgnorePublicAcls: true
      WebsiteConfiguration:
        IndexDocument: index.html
        ErrorDocument: error.html
  # S3バケットポリシー例
  BucketPolicy:
    Type: AWS::S3::BucketPolicy
    Properties:
      Bucket: !Ref StaticWebsiteBucket
      PolicyDocument:
        Version: "2012-10-17"
        Statement:
          - Sid: AllowCloudFrontAccessOnly
            Effect: Allow
            Principal: "*"
            Action: "s3:GetObject"
            Resource: !Sub "arn:aws:s3:::${StaticWebsiteBucket}/*"
            Condition:
              StringEquals:
                aws:Referer: !Ref SecretReferer # Parametersなどで指定する
  # CloudFrontディストリビューション
  CloudFrontDistribution:
    Type: AWS::CloudFront::Distribution
    # releaseステージはデータ保護のため削除を禁止し、developステージは環境の再作成を容易にするため削除を許可する
    DeletionPolicy: !If [IsRelease, Retain, Delete]
    UpdateReplacePolicy: !If [IsRelease, Retain, Delete]
    Properties:
      DistributionConfig:
        Enabled: true
        HttpVersion: http2and3
        # トップページ（例: index.html）の自動補完設定 ※サブディレクトリでは補完されないため注意
```

## 3. IaCやCI/CDのベストプラクティス

高品質なシステムを迅速に、かつバグの混入なく継続デプロイするための「CI/CD（継続的インテグレーション/継続的デプロイ）」および「モノレポ管理」の構成を規定する。

### 3.1. モノレポ（Mono-repository）による一元管理
ソースコード、インフラ定義（IaC）、データベースマイグレーション（Liquibase）、CI/CD定義（Workflows）、自動テスト、ドキュメントなど、本プロジェクトにおけるすべての資産を単一のGitHubリポジトリで管理する。
- **利点**: コミットハッシュ一つで「その時点でのソース・データベース定義・インフラ構成」が同期し、環境再現性やロールバックの確実性が担保される。

### 3.2. GitHub Actions CI/CD パイプライン構成
パイプラインは、プルリクエスト時の「静的解析・テスト・プレビューデプロイ（validate）」と、マージ後の「本番/検証環境へのリリース（deploy）」の2段階で制御される。

#### ① CI（検証・静的解析フェーズ）
プルリクエスト作成時またはブランチへのPush時、以下のステップが自動実行され、品質を担保する。
1. **コードフォーマット検証**: `cargo fmt -- --check`
2. **コンパイル検証**: `cargo check --all-targets`
3. **静的解析・Lint**: `cargo clippy --all-targets --all-features -- -D warnings`
4. **テスト用データベース起動**: PostgreSQL 16をDockerコンテナで立ち上げ、疎通確認を自動ループ待機する。
5. **マイグレーション検証**: Liquibase（v4.33.0）コンテナを使用し、`local` コンテキストの定義変更SQL（DDL/DML）を実行し、データベーススキーマを構築する。
6. **テスト実行（カバレッジ計測含む）**:
   - `cargo test --all-features -- --include-ignored`
   - プロパティベーステストや重い結合テストを含めた全件テストを実行する。

#### ② CIによる自動レビュー環境デプロイ（プレビュー機能）
プルリクエストに対して、コードベースから自動生成されたレビュー用資産を「S3 ＋ CloudFront」にアップロードし、PR固有のURL `/review/pull_request/{プルリクエスト番号}/` にデプロイする。

- **生成・配備するコンテンツ**:
  - **自動テスト結果（カバレッジ）**: `cargo-tarpaulin` によるHTMLカバレッジレポート
  - **ソースコード仕様書（Rust Doc）**: `cargo doc --no-deps` により生成された最新のAPI仕様書
  - **API実行環境（RapiDoc, Stoplight Elements）**: OpenAPI定義（`openapi.yaml`）から生成されたブラウザでテスト実行可能なSwagger/OpenAPIビューワー
  - **フロントエンド検証環境（Storybook）**: Next.jsコンポーネントを独立確認できるStorybookのビルド済み静的Web資産
  - **エンジニアリング仕様書（HonKit）**: Markdownからビルドされたプロジェクト全体のドキュメント
- **デプロイフロー**:
  - AWS OIDC 認証を用いて、GitHub ActionsからAWS環境にアクセスキーなしで一時認証。
  - レビュー資料格納用S3バケットの特定サブディレクトリに同期（`aws s3 sync`）。
  - GitHubの `createDeployment` APIを使用して、プルリクエスト画面上にプレビューURLを自動連携。
  - 差分を瞬時に確認できるよう、CloudFrontの特定パスをキャッシュクリア（`aws cloudfront create-invalidation --paths "/review/pull_request/{PR番号}/*"`）。

#### ③ CD（リリース・デプロイフェーズ）
`develop` または `release` ブランチへのマージを契機に、検証・本番環境への自動デプロイを実行する。
- **認証**: アクセスキーの漏洩リスクを完全に防ぐため、GitHub ActionsのOIDC（OpenID Connect）とAWS IAMロールを統合（`aws-actions/configure-aws-credentials`）し、一時的なクレデンシャル（Session Token）を自動取得してデプロイを実施する。
- **SAMデプロイ時の権限管理**: CI/CD専用ロール（`github-actions-ci-role`）を使用し、CloudFormationの実行自体は事前に絞られた権限を持つデプロイロール（`sam-deploy-role`）を指定（`--role-arn`）して実行することで、最小特権でのIaC適用を実現する。
- **デプロイ先区分**:
  - `develop` ブランチ: スタック名 `chat-app-develop`、リージョン `ap-northeast-3`（大阪）
  - `release` ブランチ: スタック名 `chat-app-release`、リージョン `ap-northeast-3`（大阪）
- **タグ設定の強制**:
  - タグ： `sam deploy`コマンドの実行時、引数に` --tags "Environment=${{ steps.stage.outputs.stage }} Project=${{ steps.stage.outputs.service_name }}"`を付与することでタグを強制的に付与する。これにより、IAMの設定をシンプルにする。
