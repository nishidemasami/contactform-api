# 00000007_CICD規約と実装例

本ドキュメントは、本システム開発における継続的インテグレーションおよび継続的デリバリー（CI/CD）の全体設計、自動テスト、品質検証、インフラおよびデータベースのデプロイ自動化、ならびにレビュー資料のプレビューデプロイに関するプロセスと規約を定めるものである。

---

## 1. CI/CDの設計方針

本システムにおけるCI/CDパイプラインは、以下に基づき設計・運用される。

- 開発チーム全体（開発者、レビュアー、自動ボット、およびAI共同開発エージェント）が、すべてのサブシステム（API、DB、フロントエンド、レビュー基盤、およびCI/CD定義自体）の変更に対して適用します。
- ソースコードのビルド、フォーマット・静的解析（Linter）、自動テスト（単体・結合テスト）、テストカバレッジ測定、AWS SAMを用いた各種インフラおよびアプリケーションのデプロイ、LiquibaseによるDBマイグレーション、およびSeaORMのEntity定義自動生成を行います。
- 開発中のすべてのコミットでのGitHubプッシュ（Push）時、プルリクエスト（PR）の作成・更新時、または `develop` および `release` ブランチへのマージ（Push）をトリガーとして実行されます。また、手動実行（workflow_dispatch）によるアドホックな検証・デプロイもサポートします。
- ※セキュリティ事項：GitHub Actionsの`if`に`github.event.pull_request.head.repo.fork == false`を設定することで、他者からのプルリクエスト時に意図しないCI/CDが走ってしまうのを防ぐ。
- GitHub Actionsのホスト環境（ubuntu-latest）上で各種ジョブを実行し、AWS `ap-northeast-3`（大阪リージョン）の環境（`develop`ステージおよび`release`ステージ）およびレビュー専用S3/CloudFrontバケットに対してデプロイを行います。
- **品質の恒常的担保**: 開発者が意識することなく、常にビルド可能であり、フォーマットルールが遵守され、すべての自動テストにパスしている状態を維持するため。
- **人為的ミスの完全排除**: 手動でのAWSデプロイやデータベースマイグレーションに伴う設定漏れ、セキュリティホール、接続ミスを完全に防止するため。
- **開発フィードバックサイクルの高速化**: レビュー資料（カバレッジ、Rust Doc、Stoplight APIビューワー、Storybook、TypeDoc、HonKitドキュメント）をPR単位で瞬時にプレビュー公開し、仕様の確認と相互レビューを並行かつ確実に行うため。
- **環境整合性の保証**: DSQL上の実データベースとRustコードのSeaORM Entity定義をCI/CDにより常に自動同期させ、型安全性と実装の乖離を防ぐため。
- `actions/checkout` を用いたクリーンなソースコード取得。
- GitHub Actionsの `services` 機能を利用したPostgreSQLのコンテナ起動による、クリーンかつ安定したローカルマイグレーション＆テスト。
- OIDC (OpenID Connect) を介した、セキュリティキー（AWS Access Key）を使わない一時的かつ強固なAWS認証。
- AWS SAM CLIおよびLiquibase CLI (Docker / setup-liquibase) による安全なインフラ作成およびDBテーブル構造適用。
- `sea-orm-cli` を使用したDSQL実スキーマからのEntity定義の自動生成と、GitHub Actionsボットによる自動プッシュバック。

## 2. CI/CDパイプライン一覧

本プロジェクトでは、変更対象や目的別に以下の3つの主要なパイプラインを定義・運用している。

### 2.1. CI検証パイプライン (`verify.yaml`)
- **目的**: PRおよび各ブランチへのPush時に、コード品質・フォーマット・コンパイル可能性・テストがすべて通過することを確認する。
- **トリガー**: `main`, `develop`, `release` ブランチへのPush、またはそれらに対するPR。
- **主な実行内容**:
  1. Rustのフォーマットチェック (`cargo fmt -- --check`)
  2. コンパイル確認 (`cargo check --all-targets`)
  3. Linterによる静的解析 (`cargo clippy --all-targets --all-features -- -D warnings`)
  4. GitHub ActionsサービスコンテナでのPostgreSQL起動
  5. Liquibaseを使用した `local` コンテキストでのテスト用データベース構築
  6. 全ワークスペースの自動テスト実行 (`cargo test --all-features -- --include-ignored`)
  7. SAMテンプレートの検証・静的解析 (`sam validate --lint`)

### 2.2. データベース（DB） CI/CDパイプライン (`db-cicd.yaml`)
- **目的**: データベースの定義変更（Liquibase）、データベーススタックのインフラ配備（SAM）、およびSeaORMの実体定義（Entity）の最新同期を自動制御する。
- **トリガー**: `db/**` 配下の変更、または `db-cicd.yaml` 自体の変更。
- **主な実行内容**:
  1. **検証 (validate)**:
     - SAMテンプレートのバリデーション (`sam validate --lint --template-file db/template.yaml`)
     - DB Entityプロジェクトのフォーマット、チェック、Linter検証。
     - ローカルPostgresコンテナを起動し、Liquibaseによるローカルマイグレーションがエラーなく実行できるか検証。
     - DB Entityの自動テストを実行。
  2. **デプロイ・マイグレーション (migrate)**:
     - `develop` 又は `release` へのPush時のみ動作。
     - AWS OIDCを介して、`sam deploy` を用い対象環境のDB基盤（DSQLクラスター、Lambda用IAMロール等）を更新。
     - DSQLの管理者認証トークンを動的に発行し、Docker経由でLiquibaseを実行し、対象環境のコンテキスト（`develop` 又は `release`）でマイグレーションSQLを適用。
  3. **ORM定義生成 (generate_orm)**:
     - マイグレーション完了後の最新DSQLから、`sea-orm-cli` を使用してRustのEntityコードをリバース生成。
     - 差分が存在する場合のみ、`github-actions[bot]` 名義でリポジトリに自動でコミット＆プッシュバック。

### 2.3. API CI/CDパイプライン (`api-cicd.yaml`)
- **目的**: バックエンドAPI（AWS Lambda）のインフラ（SAM）デプロイ、コンパイル・テスト検証、およびOpenAPI仕様の自動同期を自動制御する。
- **トリガー**: `api/**`, `core/**` 配下の変更、または `api-cicd.yaml` 自体の変更。
- **主な実行内容**:
  1. **検証 (validate)**:
     - Rustコードフォーマット確認 (`cargo fmt -- --check`)。
     - コンパイル確認 (`cargo check --all-targets`)。
     - Clippyによる静的解析・Linter検証 (`cargo clippy --all-targets --all-features -- -D warnings`)。
     - ローカルPostgreSQLコンテナを起動し、Liquibaseによるローカルマイグレーションを実行した上で、全ワークスペースのテストを実行 (`cargo test --all-features -- --include-ignored`)。
     - SAMテンプレートのバリデーション (`sam validate --lint --template-file api/template.yaml`)。
     - `utoipa`の自動生成バイナリを実行し、OpenAPI仕様書を `api/openapi.yaml` としてエクスポート。
     - 差分が存在する場合、GitHub Actionsボットにより `api/openapi.yaml` を自動コミット・プッシュバック。
  2. **デプロイ (deploy)**:
     - `develop` 又は `release` へのPush時のみ動作。
     - AWS OIDCを介して一時的な資格情報を取得。
     - `pip` 経由で `cargo-lambda` をインストールし、`sam build` を実行。
     - `sam deploy` によって対象環境（`develop` / `release`）のAPIスタック（API Gateway、Lambda関数等）を更新。SSM Parameter StoreからDB用の接続情報（`DbConnectLambdaRole`および`DSQLEndpoint`）を動的参照し、完全に疎結合なマルチスタック連携を実現。

### 2.4. レビュー資料管理 CI/CDパイプライン (`review-cicd.yaml`)
- **目的**: PR単位での静的仕様書、テスト結果、フロントエンドカタログ、Rust-Docなどの一括生成とホスティング。
- **トリガー**: アプリケーションコード、フロントエンド、ドキュメントの変更。
- **主な実行内容**:
  - `cargo tarpaulin` によるHTMLカバレッジレポート生成。
  - `cargo doc` によるRustドキュメント作成。
  - フロントエンドStorybookおよびTypeDocのビルド。
  - HonKitを用いたMarkdownドキュメントのHTML構築。
  - Stoplight Elements / RapiDocによるOpenAPI UI生成。
  - AWS S3へのPR別サブディレクトリ（`pull_request/{PR番号}/`）としての同期アップロード、およびCloudFrontのキャッシュ削除。
  - GitHub Deployment Statusとの連携によるPR画面へのプレビューURL自動掲載。

## 3. 実装・保守における規約事項

### 3.1. 冪等性と安全性の確保
- 全てのCI/CDステップは複数回連続で実行しても副作用が発生しないよう、べき等性を維持して設計しなければならない。
- `sam deploy` 時には `--no-confirm-changeset` を指定するが、スキーマ破壊やデータ消失を防ぐため、`release`（本番）環境用の `DeletionPolicy` / `UpdateReplacePolicy` は必ず `Retain` とし、不用意なスタック削除を排除する。

### 3.2. セキュリティおよびクレデンシャル管理
- IAM Access Keyの永続的な発行・埋め込みは**完全禁止**とする。AWSへの認証には必ずOIDC（`role-to-assume`）を使用する。
- センシティブな環境変数やパスワード（DSQL接続トークンなど）を取得、あるいは生成して使用する場合、`::add-mask::` コマンドを使用して、GitHub Actionsの実行ログ上に機密情報がプレーンテキストとして流出しないように厳重に制御する。

### 3.3. GitHub Actionsの権限管理
- 各ワークフローファイルの最上位、または各ジョブ単位で、必要最小限の `permissions`（例: OIDC用の `id-token: write`、Entityプッシュ用の `contents: write`、Deployment連携用の `deployments: write`）を明示的に指定し、デフォルトの過剰な権限付与を防止する。
- 外部GitHub Actionsは、可能な限りタグではなくコミットSHAで固定する。少なくとも `release` ブランチ向けのCDワークフローでは、サプライチェーン攻撃を抑止するためSHA pinningを原則とする。
- forkされたリポジトリからのPull Requestでは、AWS OIDC認証、デプロイ、Secret参照、外部環境への書き込みを行わない。必要に応じて `if: github.event.pull_request.head.repo.fork == false` をジョブ単位で設定する。
