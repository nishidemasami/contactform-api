# 00000002_API規約と実装例

本ドキュメントは、本システムにおけるバックエンドAPI（AWS Lambda）の設計および実装に関する規約を定めたものである。
サーバレス環境、特にリソース制限の厳しいAWS Lambda（メモリ128MB構成等）における応答性能（レイテンシ）を最大化し、コールドスタート時間を極小化するための設計原則およびコード規約を規定する。

---

## 1. 開発基本方針

本プロジェクトのAPI開発においては、以下の基本方針を遵守しなければならない。

### 1.1. クリーンアーキテクチャとDDDの適用
ビジネスロジックとインフラストラクチャを厳密に分離するため、クリーンアーキテクチャおよびドメイン駆動設計（DDD）の設計思想を適用する。
詳細なレイヤー構成、ドメインモデル定義、リポジトリ層、ユースケース層の実装方法については、[00000001_コーディング規約と実装例.md](./00000001_コーディング規約と実装例.md)を参照すること。

### 1.2. データベース権限の最小化とSQLインジェクション対策
インフラ規約およびDB規約に基づき、一般ユーザー向けの問い合わせ送信APIなどで使用するLambda実行ロールには、データベース（Amazon Aurora DSQL）の `inquiries` テーブルに対する **`INSERT` 権限のみ**を付与し、`SELECT` や `UPDATE`、`DELETE` 権限は一切付与しない。
- **実装上の制約**: SeaORMのデフォルトの `ActiveModel::insert` は自動生成キーやデフォルト値を取得するために `RETURNING` 句（暗黙的なSELECTを伴う）を実行するため、権限不足でエラーとなる。したがって、データ追加時には、プレースホルダーを用いた生SQLステートメント（`ConnectionTrait::execute_raw`）やRETURNINGを伴わないINSERT(`exec_without_returning`)を使用してINSERTを実行しなければならない。
- **セキュリティ対策**: SQLインジェクション攻撃を防止するため、文字列結合によるSQLの組み立ては厳禁とし、必ずプレースホルダー（`$1`, `$2`等）を用いてパラメータをバインドすること。
- **権限検証**: 実行時ロールには、テーブルに対するINSERT権限だけでなく、接続・スキーマ参照に必要な最小限の権限が不足していないかを検証する。特に、migration role と runtime role は分離し、runtime role で `SELECT`、`UPDATE`、`DELETE` が不要に成功しないことを結合テストで確認する。
- **CIでの必須確認**: INSERT専用ロールを使用した結合テストを用意し、`RETURNING` や暗黙的なメタデータ参照が発生しても権限エラーにならない実装になっていることを確認する。

## 2. AWS Lambda最適化設計（Cold Start対策と接続共有）

AWS Lambda上で動作するAPIハンドラーを実装するにあたり、以下のライフサイクル最適化設計を徹底すること。

### 2.1. INITフェーズ（Cold Start初期化）の有効活用
AWS Lambdaは、Cold Start時のコンテナ初期化プロセスである **「INITフェーズ」** において、追加のCPUブースト枠を割り当てる。
このブースト期間中に、実行オーバーヘッドの大きな重い初期化処理を完了させることで、リクエスト処理を実行する **「INVOKEフェーズ」** の応答レイテンシを削減する。
ただし、INITフェーズの性能特性はランタイム、メモリ設定、依存ライブラリ、ネットワーク接続、リージョン、実行環境に依存するため、「必ず高速になる」とは断定しない。重い初期化処理はINITフェーズへ寄せることを初期方針とし、CloudWatchメトリクスと実測により継続的に検証する。

- **INITフェーズ内で実行すべき処理**:
  1. ログ・トレーシング（`tracing_subscriber`）の初期化
  2. 環境変数（`DSQL_ENDPOINT`, `AWS_REGION`など）の読み込みとパース
  3. データベース（Amazon Aurora DSQL）のコネクションプールの作成と接続確立

### 2.2. INVOKEフェーズのシングルスレッド最適化
割り当てメモリが128MBの低スペック環境では、利用可能なCPUが約1/12コア（0.08コア相当）に制限される。
このような極小CPUリソース環境下でマルチスレッド非同期ランタイムを稼働させると、スレッド間のコンテキストスイッチや排他制御（Mutexロックなど）のオーバーヘッドによって性能が著しく低下する。

- **対策**: `tokio` 非同期ランタイムのマクロ設定において、明示的にシングルスレッド（`current_thread`）を指定する。
  ```rust
  #[tokio::main(flavor = "current_thread")]
  async fn main() { ... }
  ```

### 2.3. 静的ライフサイクル（OnceCell）によるコネクション・環境変数の保持
Cold Start時に生成した環境変数およびデータベース接続プール（`DatabaseConnection`）は、複数のリクエスト（Hot Start）にわたって安全に使い回せるよう、`tokio::sync::OnceCell` を用いた静的ライフサイクル変数として保持する。

## 3. APIエントリーポイント実装標準

以下に、上記の最適化設計をすべて盛り込んだバックエンドAPI（AWS Lambda）のエントリーポイントの標準コードを示す。すべてのAPIハンドラーモジュール（`main.rs`）は、この実装パターンを踏襲して作成しなければならない。

```rust
//! # バックエンドAPIデータベース Lambda ハンドラー
//!
//! このモジュールは、AWS Lambda上で動作するコンタクトフォームAPIのエントリーポイントです。
//! Amazon API Gateway HTTP API からのリクエストを受け取り、
//! HTTPメソッドやパスに基づいて適切なハンドラーにルーティングします。
//!
//! ## アーキテクチャ概要
//!
//! ```
//! クライアント
//!   └─▶ Amazon API Gateway HTTP API
//!         └─▶ AWS Lambda (このモジュール)
//!               └─▶ Amazon Aurora DSQL (SeaORM経由)
//! ```
//!
//! ## 注意点
//!
//! Cold Start 中にログ初期化と DSQL 接続を完了させ、INVOKE フェーズでは
//! 共有済みコネクションを用いて HTTP ハンドラだけを実行する構成にしています。
//!
//! ## 環境変数
//!
//! | 変数名 | 必須 | 説明 |
//! |--------|------|------|
//! | `DSQL_ENDPOINT` | ✓ | Aurora DSQLクラスターのエンドポイント |
//! | `AWS_REGION` | ✓ | Aurora DSQLクラスターのAWSリージョン |

use std::env;
use tokio::sync::OnceCell;

use presentation::lambda::{lambda_executor, function_handler::handler};
use lambda_runtime::Error;
use sea_orm::DatabaseConnection;

static DSQL_ENDPOINT: OnceCell<String> = OnceCell::const_new();
static AWS_REGION: OnceCell<String> = OnceCell::const_new();
static DATABASE_CONNECTION: OnceCell<DatabaseConnection> = OnceCell::const_new();

#[tokio::main(flavor = "current_thread")]
/// Lambda ランタイムへ型付きハンドラを登録するエントリーポイント。
async fn main() -> Result<(), Error> {
    executor().await
}

/// Lambda 処理の実態。DSQL 接続を初期化し、Lambda ランタイムへ HTTP ハンドラを登録する。
async fn executor() -> Result<(), Error> {
    // INITフェーズここから
    // INITフェーズは最大10000ms。Cold Startの初回はCPUのブースト枠が与えられるので、この間に重い処理を済ませておく。
    tracing_subscriber::fmt()
        .with_max_level(tracing::Level::INFO)
        .with_target(false)
        .without_time()
        .init();

    let dsql_endpoint = DSQL_ENDPOINT.get_or_init(|| async {
        match env::var("DSQL_ENDPOINT") {
            Ok(value) => value,
            Err(e) => {
                // 取得に失敗したら tracing でエラーログを出力
                tracing::error!(
                    "DSQL_ENDPOINT 環境変数の取得に失敗しました: {:?}",
                    e
                );
                // panic! で Lambda を終了させる(Fail-Fast)
                panic!("Internal Server Error");
            }
        }
    }).await;

    let aws_region = AWS_REGION.get_or_init(|| async {
        match env::var("AWS_REGION") {
            Ok(value) => value,
            Err(e) => {
                // 取得に失敗したら tracing でエラーログを出力
                tracing::error!(
                    "AWS_REGION 環境変数の取得に失敗しました: {:?}",
                    e
                );
                // panic! で Lambda を終了させる(Fail-Fast)
                panic!("Internal Server Error");
            }
        }
    }).await;

    let db = DATABASE_CONNECTION.get_or_init(|| async {
        use infrastructure::db::{config::DatabaseConfig::AuroraDSQL, connection::create_connection};
        // 非同期接続処理を OnceCell の中で非同期的に完了させる
        // ※実際の実装にあたっては初期化フローでのエラーハンドリングを厳密に行うこと
        create_connection(&AuroraDSQL {
            role: "insertonly".into(),
            endpoint: dsql_endpoint.as_str().into(),
            region: aws_region.as_str().into(),
        })
        .await
        .unwrap_or_else(|e| {
            tracing::error!("データベース接続の初期化に失敗しました: {:?}", e);
            panic!("Database Connection Error");
        })
    }).await;

    // INITフェーズここまで
    // INITフェーズが10000ms以内に終わらなかった場合、初期化に失敗したと判断され再起動してしまうので注意。

    // INVOKEフェーズここから
    // INVOKEフェーズは、初期方針としてシングルスレッドで実装し、パフォーマンスチューニングを実施する場合は最適値を実測で判断する。
    lambda_executor(|event| {
        // Hot StartではCold Startで作成した共有済みコネクションをcloneしてHTTPハンドラを実行する。
        let repository: Arc<dyn InquiryRepository> =
            Arc::new(SeaOrmInquiryRepository::new(db.clone()));
        handler(Arc::clone(&repository), event)
    })
    .await
}

#[cfg(test)]
mod tests {
    use super::*;
    use rstest::*;

    #[tokio::test]
    #[ignore = "ローカルPostgreSQLの起動が必要なためデフォルトでは実行しない"]

        let db = DATABASE_CONNECTION.get_or_init(|| async {
            use infrastructure::db::{config::DatabaseConfig::PostgreSQL, connection::create_connection};
            // 非同期接続処理を OnceCell の中で非同期的に完了させる
            // ※実際の実装にあたっては初期化フローでのエラーハンドリングを厳密に行うこと
            create_connection(&PostgreSQL {
                host: "localhost".into(),
                port: 5432,
                database: "postgres".into(),
                username: "insertonly".into(),
                password: "insertonly".into(),
            })
            .await
            .unwrap_or_else(|e| {
                tracing::error!("データベース接続の初期化に失敗しました: {:?}", e);
                panic!("Database Connection Error");
            })
        }).await;
    }

    /// テスト用のモックリポジトリ
    pub struct MockInquiryRepository {
        pub error_to_return: Mutex<Option<InquiryRepositoryError>>,
    }
    
    impl Default for MockInquiryRepository {
        fn default() -> Self {
            Self::new()
        }
    }
    
    impl MockInquiryRepository {
        pub fn new() -> Self {
            Self {
                error_to_return: Mutex::new(None),
            }
        }
    
        pub fn set_error(&self, err: InquiryRepositoryError) {
            *self.error_to_return.lock().unwrap() = Some(err);
        }
    }
    
    #[async_trait]
    impl InquiryRepository for MockInquiryRepository {
        async fn save(&self, inquiry: Inquiry) -> Result<Inquiry, InquiryRepositoryError> {
            let err = self.error_to_return.lock().unwrap().clone();
            if let Some(e) = err {
                return Err(e);
            }
            Ok(inquiry)
        }
    }
    
    #[rstest]
    #[tokio::test]
    async fn 何らかのテスト(#[future(awt)] repository: Arc<dyn InquiryRepository>) {
        // 何らかのテストを実装する
    }
}
```

### 3.4. 実装における注意点 (Fail-Fast原則)
- 起動時に必要な環境変数（`DSQL_ENDPOINT`、`AWS_REGION`）が設定されていない場合、またはデータベース接続の初期化に失敗した場合は、**その時点で即座に `panic!` させてプロセスを終了（Fail-Fast）** させなければならない。
- 不完全な初期化状態のままリクエストを処理し始めると、無駄な呼び出しコストの増加やシステム全体の不安定化を招くため、早期のエラー検知とコンテナの再起動（再クリーン初期化）を優先する。
